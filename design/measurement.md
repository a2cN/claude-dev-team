# 計測とメタデータログの設計書

作成日: 2026-10-12 / ステータス: **案(レビュー待ち)**
関連: `LOGGING.md`(使い方)、`templates/STATUS.md`(記録の書式)、`agents/quality-assurance.md`(failure tag)

この文書は「なぜこう測るのか」を書く。手順は `LOGGING.md`、書式は `templates/STATUS.md` にあり、この文書と食い違ったら、この文書を直してから両方を直す。

各決定には、**検討した選択肢、比べた観点、選んだ理由、あきらめたもの** を書く(§8)。

---

## 1. 目的: 数字で何を判断するか

計測は、次の3つの判断のためにある。判断に使わない数字は取らない(取るだけでトークンと手間がかかる)。

| # | 判断 | 使う数字 |
|---|---|---|
| J1 | ハーネスの変更(例: ハンドオフ書式の変更)を **残すか戻すか** | ステージあたりのトークン(主指標)と、品質のガード指標 |
| J2 | 実行中の run を **止めて人間に回すか**(HOTL の停止条件) | ステージのトークン、REJECT 回数、エスカレーション |
| J3 | Process Advisor が出す改善提案の **根拠** | REJECT の原因タグの分布、どのステージが重いか |

優先順位は **①トークン削減 ②品質**。品質は「悪化したら①の施策を戻す」ためのガードとして使う。

## 2. 用語

| 用語 | 意味 |
|---|---|
| run | 1つのタスク(`<task-slug>`)を、パイプラインで最初から完了まで流す1回。やり直しは `<task-slug>` の2回目の run |
| ステージ | サブエージェントの **1回の起動**。同じロールの2回目(開発者の手戻り rev2 など)は別のステージ |
| オーケストレーター | ステージを順に起動する側。会話中のメインの Claude、または人間。ロール名 `ORCHESTRATOR` |
| セッション記録 | Claude Code が自動で書く会話の記録(`~/.claude/projects/...`)。§3 |
| Event Log | `STATUS.md` の追記専用の年表。この設計では **メタデータログを兼ねる**(§4) |
| 入力換算トークン | 種類ごとに料金の比で重みを付けて、1つの数字にしたもの(§6.1) |

## 3. 情報源と信頼度

| 情報源 | 中身 | 誰が書く | 信頼度 |
|---|---|---|---|
| セッション記録(メイン) | オーケストレーターの全応答の `usage`(4種類、モデル、時刻) | Claude Code が自動で | 高い。ただし形式は公式に文書化されていない |
| セッション記録(サブエージェント) | 1起動=1ファイル。`meta.json` にロール名 | 同上 | 同上 |
| Event Log(`STATUS.md`) | run・ステージ・判定・ゲート・停止・トークンの記録 | オーケストレーター、各ロール | 中。書き忘れがありうる(§9) |
| `60_qa_report.md` | 不具合ごとの failure tag | QA | 中。分類はモデルの判断 |
| `docs/OPEN-DECISIONS.md` | 未決事項 | 各ロール、人間 | 高い(verify スクリプトで照合) |

## 4. メタデータログのデータモデル

### 4.1 1行の書式

Event Log の既存の書式 `<日付> — <ROLE> — <何が起きたか>` を拡張する。**機械で読む行** は、イベント名と `key=value` を持つ。人間向けの自由記述の行は、これまでどおり書いてよい(集計では無視される)。

```
- <時刻> — <ROLE> — <event> <key=value ...> [— <自由記述>]
```

- `<時刻>`: ISO 8601、秒まで、タイムゾーン付き(例 `2026-10-12T13:05:09+09:00`)。**シェルの `date -Iseconds` の出力を使う**。モデルに時刻を書かせない(§8 D5)。
- `<ROLE>`: `ORCHESTRATOR`、`HUMAN`、各ロール名(`PM`、`DEVELOPER`、`QA` など既存どおり)。
- 値に空白を含めない。自由記述は最後の `—` の後ろに置く。

### 4.2 イベントの一覧

| event | 誰が | 必須のキー | 例 |
|---|---|---|---|
| `run-start` | ORCHESTRATOR | `run` | `run-start run=scaffold-1` |
| `stage-start` | ORCHESTRATOR | `stage`、`rev` | `stage-start stage=developer rev=1` |
| `stage-end` | ORCHESTRATOR | `stage`、`rev`、`outcome`(ok / blocked / escalated) | `stage-end stage=developer rev=1 outcome=ok` |
| `verdict` | QA | `rev`、`result`(PASS / REJECT)、`tags` | `verdict rev=2 result=REJECT tags=spec:1,impl-bug:2` |
| `gate` | HUMAN | `gate`(plan / design / completion)、`result`(APPROVED / REJECTED / REVIEWED) | `gate gate=design result=APPROVED` |
| `escalate` | どのロールも | `trigger`(§7 の6種)、`ref`(OD の ID など) | `escalate trigger=od ref=OD-scaffold-01` |
| `human-fix` | HUMAN | `what`(code / doc / config) | `human-fix what=code — 完了後に手で直した` |
| `tokens` | ORCHESTRATOR | `scope`(stage / run)、4種類の数、`requests` | `token-report.py` の出力を貼る |
| `run-end` | ORCHESTRATOR | `run`、`outcome`(done / abandoned) | `run-end run=scaffold-1 outcome=done` |
| `correction` | 誰でも | `ref`(訂正する行の時刻) | 追記専用なので、誤りは訂正の行で直す |

`stage-start` / `stage-end` は、ステージのトークンを測るためには **必須ではない**(§5)。人間が年表として読むため、また停止したステージを特定するために書く。

## 5. 突き合わせ方: トークンとイベントをどう結ぶか

**run の範囲は Event Log の時刻で決め、ステージの内訳はサブエージェントのファイルで決める。**

```
Event Log:  run-start 13:00 ──────────────────────────────── run-end 15:40
                │                                                  │
セッション記録: [メイン: オーケストレーター分 ─────────────────────────────]
              [agent-a.jsonl: product-manager]
                           [agent-b.jsonl: developer rev1]
                                          [agent-c.jsonl: quality-assurance]
                                                    [agent-d.jsonl: developer rev2]
```

1. `run-start` と `run-end` の時刻で、セッション記録の範囲を切る(`--since` / `--until`)。
2. 範囲内のサブエージェントのファイル1つ=ステージ1つ。ロール名は `meta.json`、rev は起動の順番で決まる。
3. 範囲内のメインの応答=オーケストレーションの費用(ステージの合間の判断、報告、ファイル確認)。
4. run 全体=2と3の合計。

**運用上の約束**: 1つのセッションで、同時に2つの run を流さない(範囲が重なり、どちらの run か区別できない)。

## 6. 指標の定義

### 6.1 主指標: ステージあたりの入力換算トークン

```
入力換算 = input × 1
         + cacheCreation(5分) × 1.25
         + cacheCreation(1時間) × 2
         + cacheRead × 0.1
         + output × 5
```

重みは Claude の料金表での入力単価に対する比。料金が変わったら、この表と `token-report.py` の1か所を直す。4種類それぞれの生の数も、必ず並べて記録する(重みで隠れる変化を見落とさないため)。

**モデルが違うと比べられない。** 入力換算は「同じモデルの中での重さ」で、モデルの単価の違い(Opus と Haiku など)は入っていない。比較は同じモデルのステージ同士で行う。ロールのモデルを変える施策(例: 開発者を Sonnet から Haiku へ)を評価するときだけ、料金表の単価を掛けて比べる。

| 指標 | 計算 | 判断 |
|---|---|---|
| ステージの入力換算 | §5 の2のファイルごと | J1(同じロール同士で比べる)、J2(予算) |
| オーケストレーション費用 | §5 の3 | J1(私が重くなっていないか) |
| run の入力換算 | §5 の4 | 参考。タスクの大きさに左右されるので、J1 には使わない |
| ステージの起動回数 | ファイルの数 | 固定費(1起動 約1.3万トークン)の見積もり |

### 6.2 品質のガード指標(悪化したら J1 の施策を戻す)

| 指標 | 出所 | なぜガードになるか |
|---|---|---|
| 人間の差し戻し回数 | `gate ... result=REJECTED` | エージェントが操作できない |
| 完了後に人間が直した回数 | `human-fix` | 同上。HOTL では完了承認が無いので、これが主な品質信号になる |
| マージ後に見つかった不具合 | Issue(ラベル `found-after-merge`) | 同上 |

### 6.3 補助指標(単独では判断に使わない)

| 指標 | 出所 | 注意 |
|---|---|---|
| QA 初回合格率 | `verdict` | QA 自身も改善の対象なので、これだけで品質を判断しない |
| REJECT の原因タグの分布 | `verdict` の `tags` | J3 の根拠。`spec` が多ければ上流、`impl-bug` が多ければ開発者を直す |
| 必読の成果物を読んだ率 | 各成果物の Inputs Read | 「入力に無いものは出力に無い」の検出 |

### 6.4 比べ方の決まり
- タスクの合計ではなく、**同じロールのステージ同士** で比べる。
- 1回の比較で結論を出さない(同じ入力でも結果が揺れる)。次の数タスクで主指標が下がり、ガード指標が悪化していなければ残す。
- 変更の前に「どの指標を、どちらに、どれだけ動かす想定か」を書く。

## 7. HOTL との対応: どの数字で止まるか

| 停止条件 | 判定に使うもの | 判定する人 |
|---|---|---|
| 未決事項が出た | `escalate trigger=od` | 書いたロール |
| QA が2回 REJECT | `verdict` の REJECT の数 | QA(既存の上限ルール) |
| トークン予算の超過 | ステージの入力換算 > 予算 | オーケストレーター(ステージ終了時に `token-report.py` を実行) |
| 要件・ADR と矛盾 | `escalate trigger=contradiction` | 気づいたロール |
| 保護パスに触れた | `escalate trigger=protected-path` | hook、またはロール |
| UI のモックが無い | `escalate trigger=no-mock` | デザイナー、開発者(既存ルール) |

予算の値は未定。**タスク#1 の基準値を見てから決める**。それまでは、超過で止めずに記録だけする。

## 8. 決めたことと理由

### D1. トークン数の出所

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| A. OpenTelemetry(標準テレメトリ) | 公式の仕組み。チームで集計基盤があるなら最適 | ロール名が `custom` に伏せられる(出すとツールの詳細まで出る)。ファイル出力が無く、集計サーバーか画面出力が必要。**有効化し忘れた run は記録ゼロ** |
| **B. セッション記録(採用)** | 常に自動で書かれる。ロール名、モデル、4種類が揃う。設定ゼロ | 形式が公式に文書化されていない。1応答が複数行に分かれる罠がある |
| C. `/cost` などの画面表示を人が書き写す | 簡単 | ロール別に分からない。書き写しの誤り |
| D. エージェントに自己申告させる | 簡単 | モデルは自分の使用量を知らない。数字を作ってしまう |

**理由**: 一番重視したのは「基準値を取り逃さないこと」。A は設定を忘れると取り戻せない。B は何もしなくても残る。形式が変わる危険は、テストと「Claude Code を更新したら1回確かめる」で受け止める。**あきらめたもの**: 公式の、安定した仕組みであること。

### D2. メタデータログ(パイプラインのイベント)の置き場所

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **A. STATUS.md の Event Log に寄せ、1行の書式を固定する(採用)** | 記録先が1か所。人間も読める。既に archive の仕組みに乗っている。追加のトークンがほぼ無い | Markdown を読むので、書式の崩れに弱い |
| B. 別の JSONL ファイル(`.claude-dev-team/logs/<run>.jsonl`) | 機械で確実に読める | 記録先が2か所になり、食い違う。各ロールが2回書く(トークンが増える)。archive の仕組みを作り直す |
| C. 両方(Event Log は人間用、JSONL は機械用) | それぞれ最適 | B の悪い点が全部残る。二重管理 |
| D. hook が自動で JSONL を書く | 書き忘れが無い | ステージの意味(rev、判定、タグ)を hook は知らない。作るのに手間 |

**理由**: 優先順位①のトークン削減と、「真実の置き場所は1つ」(DOCUMENT-POLICY の原則)を重視した。B と C は、同じ事実を2か所に書かせるので、トークンも食い違いも増える。書式の崩れは、後で verify スクリプトに書式チェックを足せば機械的に防げる。**あきらめたもの**: 機械での読みやすさ。読み取りが本当につらいと分かったら D を足す(01 §7 Step 3 の候補として残す)。

### D3. ステージとトークンの結び付け方

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| A. オーケストレーターが `stage-start` / `stage-end` の時刻を書き、その区間で切る | 仕組みが単純 | 書き忘れると、そのステージは測れない。時刻の誤り |
| **B. サブエージェントのファイル1つ=ステージ1つとして自動で分ける(採用、run の範囲は A の方式)** | 書き忘れが起きない。ロール名も自動 | オーケストレーター自身の分は、ステージに割り振れない(別の指標にする) |
| C. 指示文に run ID を埋め込み、記録を検索する | run を確実に特定できる | 指示文が長くなる(トークン増)。検索がもろい |
| D. OTel の属性で結ぶ | 正確 | D1 で不採用 |

**理由**: 実機で、サブエージェントは1起動ごとに別のファイルになり、時刻とロール名を持つと確かめた。人間の書き忘れに頼る部分を、run の始めと終わりの2行だけに減らせる。**あきらめたもの**: オーケストレーター分のステージ別の内訳(合計として別に見る)。

### D4. 「トークン」を1つの数字にする方法

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| A. 4種類の単純な合計 | 簡単 | ほぼ cacheRead(安い)で決まり、削減の効果が見えない |
| B. output だけ | 生成量が分かる | 読み込みの重さ(長い指示文、大きなファイル)が見えない |
| C. 金額(ドル) | 実感がある | サブスクリプションでは実際の請求額と一致しない。料金改定で過去と比べられなくなる |
| **D. 入力換算トークン(料金の比で重み付け、採用)** | 重さの実態に近い。単位がトークンのまま | 重みの根拠(料金表)を保守する必要 |

**理由**: 「どこを削れば効くか」を正しく示すことを重視した。A は誤った方向に導く(cacheRead を減らす施策が過大に見える)。**あきらめたもの**: 単純さ。生の4種類も必ず並べることで補う。

### D5. 時刻をどこから取るか

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| A. モデルが書く | 手間なし | モデルは今の時刻を正確に知らない。もっともらしい時刻を作ってしまう |
| **B. シェルの `date -Iseconds` の出力を貼る(採用)** | 正確 | コマンドを1回実行する手間 |
| C. 時刻を書かず、セッション記録の時刻だけ使う | 書く手間なし | Event Log だけで年表として読めなくなる |

**理由**: 時刻は run の範囲を切る鍵なので、正確さを最優先した。

### D6. この設計書の置き場所と言語

| 選択肢 | 良い点 | 悪い点 |
|---|---|---|
| **A. claude-dev-team の `design/measurement.md`、日本語(採用)** | 他のプロジェクトでも使える汎用の設計として、ハーネスと一緒に管理できる。今の主な読み手(人間)が読みやすい | ほかの文書は英語 |
| B. もっちりの docs | 書きやすい | ハーネスの設計なのに、1プロジェクトに閉じる |
| C. claude-dev-team の `docs/design/` | よくある配置 | 利用側プロジェクトの「デザインの正典」(`docs/design/`)と名前がぶつかり、紛らわしい |

**理由**: 汎用性と紛らわしさの回避。英語版は、還元の段階で必要になったら作る。

## 9. 保存・秘密・保存期間

| もの | 置き場所 | git | 秘密の扱い |
|---|---|---|---|
| セッション記録 | `~/.claude/projects/` | 入れない | **中身はすべて秘密扱い**。数を数えるだけで、抜粋も外に出さない |
| Event Log | workspace → 完了時に `docs/archive/` | archive は commit する | 秘密、鍵、個人情報を書かない。数字と ID と短い説明だけ |
| QA レポート | 同上 | 同上 | 同上 |

**保存期間の注意**: Claude Code は古いセッション記録を自動で消す(設定 `cleanupPeriodDays`、既定は30日)。だから run の終わりに `tokens scope=run` を Event Log に必ず書く。書かなかった run は、30日後に測れなくなる。

## 10. 既知の限界

- **セッション記録の形式は公式に文書化されていない。** 変わると、テストは通ったまま、本番の集計がゼロになる。Claude Code を更新したら、実際の run で1回確かめる。
- **Event Log の書き忘れ。** `run-start` / `run-end` を忘れると、範囲が切れない。将来 verify スクリプトで、書式と必須イベントの有無を確かめる。
- **failure tag はモデルの判断。** 分類がぶれる。分布の傾向を見る用途に留め、1件ずつの正しさには頼らない。
- **会話の要約(compact)の分。** メインの要約もトークンを使い、オーケストレーション費用に含まれる。区別はしない。
- **サンプルが少ない。** 統計的な有意性は求めない(§6.4)。
